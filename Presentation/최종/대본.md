## 8. 기술 프레임워크 · R&R — 0:45

먼저 프론트엔드는 사용자가 MAKO를 만나는 접점을 담당합니다. 

PC에서는 이동과 전투, 작업처럼 즉각적인 게임 경험을 처리하고, 모바일에서는 게임 밖에서도 대화와 요청을 이어갈 수 있게 합니다.

백엔드는 이 두 접점에서 들어온 요청을 확인하고, 사용자와 MAKO의 대화와 맥락을 하나로 연결합니다. 그리고 AI가 현재 상황에 맞는 답변과 행동을 제안할 수 있도록 필요한 정보를 전달합니다.

정리하면 프론트엔드는 사용자 경험과 실제 동작을, 백엔드는 기기 간 연결과 AI 처리를 맡습니다.

엔진은 플레이와 MAKO의 행동을, 백엔드는 PC와 모바일의 연결을, 아트는 월드와 캐릭터를 맡았고, AI는 대화와 기억을 담당했습니다.

각 파트의 결과를 하나의 MAKO 경험으로 통합한 융합 프로젝트입니다.

그리고 기기가 바뀌어도 같은 MAKO로 느껴지려면, 대화의 기억도 같은 근거 위에서 이어져야 합니다.

# Appendix 질의응답용

## A. 기존 장기기억 상세

장기기억은 대화와 게임 사건의 원문에서 후보를 만들고, 출처와 사용자 범위를 확인한 뒤 활성 기억으로 전환합니다. 회상할 때는 같은 사용자와 세이브, 동료의 관련 기억만 최대 3개, 360자까지 전달하고, 답변이 원문의 숫자나 부정 의미를 바꾸지 않았는지도 다시 확인합니다. 오래된 기억은 바로 지우지 않고 검색 순위만 낮추며, 사용자는 기억을 정정·고정·삭제할 수 있습니다.

## B. 기존 멀티플랫폼 상세

웹앱에서는 대화와 기억 관리를, Discord에서는 게임 밖 작업 요청을, KakaoTalk에서는 일상 속 대화를 보여줍니다. 게임에서 쌓은 사건은 일상의 대화로 이어지고, 일상에서 나눈 이야기는 다시 게임 속 MAKO에게 돌아옵니다. 플랫폼별 화면은 달라도 같은 정체성과 기억을 공유하는 하나의 동료 경험입니다.

## C. R&R

엔진은 플레이와 MAKO의 행동을, 백엔드는 PC와 모바일의 연결을, 아트는 월드와 캐릭터를 맡았고, AI는 대화와 기억을 담당했습니다. 각 파트의 결과를 하나의 MAKO 경험으로 통합한 융합 프로젝트입니다.

## D. Physical AI

Physical AI는 현재 구현 범위가 아니라 다음 확장 방향입니다. PC와 모바일에서 이어지던 MAKO의 정체성과 관계 맥락을 반려 로봇 같은 현실 디바이스로 옮기는 개념입니다. 핵심은 기기 수를 늘리는 것이 아니라, 화면 밖에서도 사용자가 같은 동료를 만난다고 느끼게 하는 것입니다.

## E. 생성형 AI 활용

생성형 AI는 결과를 대신 결정하는 도구가 아니라 탐색과 반복을 빠르게 만드는 제작 도구로 사용했습니다. 캐릭터 콘셉트 비교, UI 구성, 발표용 비주얼 초안, 코드와 백엔드 구조 점검에 활용했고, 무엇을 채택하고 어떻게 수정할지는 팀이 직접 판단했습니다. 게임 안에서도 같은 원칙을 적용해 AI 출력은 후보로만 받고, 실제 행동은 게임 규칙으로 다시 검증합니다.

## F. FAIREWorldContextV1이 판단 입력을 만드는 구조

이 페이지는 MAKO가 무엇을 읽고, 어떤 형식으로 다음 판단에 넘기는지 보여줍니다. `FAIREWorldContextBuilder::Build`가 `ThreatComponent`, `WorkOrderComponent`, MAKO와 공유 보관함의 인벤토리 스냅샷, 주변 작업대·자원 조회 결과를 한 번에 모읍니다. 이렇게 만든 `FAIREWorldContextV1`에는 위치, 위협 수, 주변 자원, 사용 가능한 작업대, 현재 작업, 인벤토리가 들어갑니다. 입력을 만들기 전에 Stable ID와 Actor·World 유효성, MAKO·Storage `SessionId` 일치 여부를 확인하고, 허용 목록과 배열 상한도 적용합니다. 조건이 맞지 않으면 판단에 사용할 데이터를 억지로 채우지 않고 빈 Context로 반환합니다.

## G. StateTree와 GAS의 로컬 실행 경계

여기서는 상태 선택과 실제 게임 수치 변경의 경계를 분리했습니다. `AI Perception`이 위협을 감지하면 `ThreatComponent`가 거리와 `HoldFire`·`DefendPlayer`·`Aggressive` 정책으로 유효한 타깃을 고릅니다. 그 결과를 `StateTree`가 `Disabled → Survival → Combat → Support → DirectCommand → Work → Return / Idle` 우선순위로 평가합니다. 전투는 `EventAttackRequest`, 지원은 `EventSupportHealRequest`로 Gameplay Event만 보냅니다. 타깃·거리·쿨다운·아이템 검증과 Attribute 변경은 GAS Ability가 맡습니다. 타깃이 사라지거나 사망하거나 정책이 바뀌면 이동과 Ability를 정리하고 Return 또는 Follow로 돌아갑니다. 따라서 StateTree가 Health·Stamina를 직접 변경하지 않는 것이 핵심 경계입니다.

## H. Offline Task의 WebApp·Backend·UE5 동기화 계약

오프라인 작업은 서버 상태와 UE 저장을 분리해 동기화합니다. WebApp은 `POST /api/v1/tasks`로 작업을 만들고 `GET`으로 목록을 조회하며, 게임 인벤토리를 직접 지급하지 않습니다. Backend는 서버 시계로 `Pending → InProgress → Completed → Claimed` 상태와 `progress_quantity`·`result_quantity`를 관리합니다. 다시 접속한 UE5의 `SyncOfflineTasks()`가 목록을 파싱·검증하고 `start → complete`를 호출한 뒤, 완료 결과를 `TryApplyOfflineTaskResult`로 Inventory에 원자 적용합니다. `RequestInventorySave` 성공을 확인한 다음에만 `claim`을 호출합니다. `X-Request-ID`, World·Inventory `SessionId`, 저장 후 Claim이라는 경계를 지켜 중복 적용과 다른 세션의 결과 반영을 막습니다. 현재 구현은 이 계약을 연결하는 클라이언트 프로토타입이며, 각 단계의 실패는 `Failed`로 종료하고 자동 재시도하지 않습니다.
